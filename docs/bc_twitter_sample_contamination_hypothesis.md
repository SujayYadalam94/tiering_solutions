# May performance hypothesis: background activity enters ARMS's hotness signal

September 11, 2026. Source and notes investigation only; no benchmark or host
setting was changed.

The proposed new experiment is to distinguish **ordinary resource contention
from contamination of ARMS's page-access measurements**. A different population
or placement of background threads could change ARMS's decisions even with the
same script, kernel, graph, model and amount of free DRAM.

This connects two previously documented observations. The filtering asymmetry
is already in [the source-reversion audit](arms_reversion_candidates.md), and
incomplete thread affinity is already in [the setup-knob audit](bc_twitter_setup_knobs.md).
Neither is a newly discovered source change. I found no completed experiment in
the reviewed notes that isolates their interaction as a cause of the May gap.

## Source evidence

* [arms_kernel.cpp](../arms_kernel.cpp:1032) opens sampling events with
  `perf_event_open(&pe, -1, cpu, -1, 0)`, retaining IP, PID/TID and address.
  This observes all processes/threads on that CPU, according to
  [perf_event_open(2)](https://www.man7.org/linux/man-pages/man2/perf_event_open.2.html).
  `exclude_kernel=1` excludes kernel execution, not other userspace processes.
* [pebs_scan_thread.cpp](../pebs_scan_thread.cpp:378) gates PID, runtime-thread,
  preload-IP and helper-library-IP exclusions behind
  `!ENABLE_MIGRATION_WORKERS || VIRTUAL_FEATURES_ENABLED`. Ordinary ARMS has
  workers enabled and virtual features disabled; the model has virtual features
  enabled. Thus ordinary ARMS bypasses these exclusions while the model uses them.
* Eligible samples reach `get_or_create_tracked_page()` and increment hotness.
  [Page keys](../arms_kernel.cpp:466) contain the 2 MiB aligned virtual address,
  without the originating PID. The kernel/logging-address checks do not establish
  that an address belongs to the benchmark. Migration subsequently uses
  `numa_move_pages(0, ...)`, meaning the benchmark's own address space.
* [setup.sh](../setup.sh:57) uses `taskset -pc` on process IDs. Existing secondary
  threads need not follow the main thread; applying affinity to all threads is
  the separate `--all-tasks` operation documented in
  [taskset(1)](https://www.man7.org/linux/man-pages/man1/taskset.1.html).
* The May 4 Git source at `8d6a8bc66` contains the same filter condition, CPU-wide
  event setup and helper list (including libgomp). The frozen May setup also
  contains the main-thread affinity operation. This is an existing exposure to
  changing runtime activity, not evidence of a new September feature.

## Proposed mechanism and its limits

Suppose a pre-existing editor/service worker remains eligible for a sampled fast
CPU after setup. Its samples can introduce addresses into ARMS's page map. If a
foreign virtual address overlaps a benchmark range, it can inflate that range's
apparent hotness; otherwise it can create irrelevant records and potentially
unsuccessful migration work. The model rejects the foreign PID before this
ordinary page accounting. Actual persistence and selection of those records
depend on the scanner and policy and have not been measured here.

This can change ARMS more than the model without a large loss of node-0 memory.
The existing finding that editor/service RSS resides on node 1 therefore does
not exclude this mechanism: memory residence does not determine execution CPU.
Nor does excluding overlapping BC/PR benchmark processes exclude other workers.

There is a related same-process possibility: ARMS accepts accesses generated by
its own workers and helper libraries, while the model filters them. Scheduling,
allocation or OpenMP-runtime activity could change those contributions. Test
this separately from foreign-PID contamination so a result has a clear cause.

No recovered May sample-origin trace or per-thread execution record establishes
that contamination was greater then. It could also have been negligible.
Repeated slow May runs would require a sufficiently persistent source of activity;
a single brief service wakeup would be a weak explanation. The workload-dependent
BC/PR results also preclude assuming a uniform slowdown across all applications.

## Discriminating experiment

1. In isolated candidate libraries, count incoming samples **before** existing
   filters: foreign PID, tiering TID, preload/helper IP, and remaining application
   samples. Use mutually exclusive categories and record CPU and read/write type.
   Track how much foreign activity survives address eligibility and contributes
   to selected pages. Existing `filtered_other_pid=0` output from ordinary ARMS
   is not proof of clean samples: that counter is updated only inside the bypassed
   filter. Keep diagnostic counters out of migration-cost timers and avoid
   per-sample printing.
2. Compare unchanged ARMS against an otherwise identical ARMS build that rejects
   **only foreign PIDs**. Keep the model fixed. Do not enable virtual features or
   switch to the model build merely to turn filtering on.
3. Repeat both ARMS variants under quiet conditions and with the same controlled
   background memory-access worker on a sampled CPU, allocating its memory on
   node 1. Keep that worker's CPU/memory behavior identical across variants and
   retain the existing preparation and frozen model. This separates the extra
   effect of sample contamination from the worker's shared resource contention.
4. Alternate/repeat cases and record read time, individual BC iterations,
   accepted sample origins, selected/moved pages, migration errors and compaction
   deltas. Measure initial free DRAM and per-thread CPU placement in every case.

Support would be a larger background-induced ARMS penalty without the PID filter,
alongside foreign samples affecting selection. If foreign samples are negligible
or excluding them does not change the penalty, deprioritize this branch. Only
then consider a separate same-PID runtime/helper-filter experiment.

An induced effect would establish sensitivity, not recover the historical cause.
Restoring the original approximately 15.7-second gap would still need the model
near its historical absolute runtime and evidence connecting the intervention
to May. The completed perf-rate-cap experiment does not test sample origin;
the completed compaction and storage tests do not isolate it either.
