# Compaction settings: what the isolation tests can establish

The complete local kernel tree is the modified 6.2 tree at `/users/zimooo2/linux-hybridtier`; the installed 6.18 tree contains headers only. The paths below were checked against upstream Linux **v6.18**, with the matching local 6.18 GFP definitions verified in `/usr/src/linux-headers-6.18.1-061801/include/linux/gfp_types.h:388` and `gfp.h:419`. This is source-path evidence, not a trace attributing time to a particular process.

**THP destination migration can directly compact regardless of the top-level THP defrag setting.** May4 [migration_worker.cpp](../source/may04/migration_worker.cpp) calls `numa_move_pages` at line 259. Linux's syscall path selects the requested node, uses synchronous migration, and allocates large-folio destinations with `GFP_TRANSHUGE` while retaining `__GFP_THISNODE`. That allocation flag permits direct reclaim/compaction; the migration allocator never consults the THP defrag switch. [v6.18 migrate.c, lines 2031–2089](https://github.com/torvalds/linux/blob/v6.18/mm/migrate.c#L2031). Local 6.2 equivalents are `mm/migrate.c:1645` and `:1700`.

**Top-level THP `defrag=always` still affects application allocation during graph loading.** The anonymous hugepage fault path obtains its allocation flags from `vma_thp_gfp_mask`; `always` permits direct stalls, whereas `never` uses the lighter allocation path. [v6.18 huge_memory.c, lines 1104–1110 and 1216–1236](https://github.com/torvalds/linux/blob/v6.18/mm/huge_memory.c#L1216). GAPBS allocates and fills adjacency arrays during `ReadSerializedGraph` (`/users/zimooo2/gapbs/src/reader.h:287`), so changing defrag may affect read-phase allocation latency, THP coverage, and later migration behavior. This is an inference from the two source paths, not proof that the graph read stalled there. It is not a direct on/off switch for migration compaction.

**`compact_fail` is an allocation-path counter, not an attribution to kcompactd.** `__alloc_pages_direct_compact` increments `compact_stall` when compaction was not skipped, then increments success if an allocation succeeds or fail otherwise. The allocator may revisit this path; event counts are neither time measurements nor one-to-one migration counts. These global counters may include ARMS workers, application faults, khugepaged allocations, or other callers. [v6.18 page_alloc.c, lines 3808–3865](https://github.com/torvalds/linux/blob/v6.18/mm/page_alloc.c#L3808). Local equivalent: `mm/page_alloc.c:4476`.

**Proactiveness 80→20 tests background policy, not direct compaction.** It raises the fragmentation threshold for proactive work; even zero would leave allocation-triggered direct compaction and demand-triggered kcompactd work available. In 6.18, `compact_daemon_migrate_scanned` and `compact_daemon_free_scanned` cover both proactive and demand background scans. `compact_daemon_wake` is incremented in the demand-work path, so zero wakes alone does not exclude proactive scanning. [v6.18 threshold logic](https://github.com/torvalds/linux/blob/v6.18/mm/compaction.c#L2060), [proactive accounting](https://github.com/torvalds/linux/blob/v6.18/mm/compaction.c#L2716), [demand accounting](https://github.com/torvalds/linux/blob/v6.18/mm/compaction.c#L2863), [kcompactd loop](https://github.com/torvalds/linux/blob/v6.18/mm/compaction.c#L2962).

**Khugepaged scan sleep is another separate control.** Raising `scan_sleep_millisecs` spaces its background collapse scans. Its own `khugepaged/defrag` setting determines whether its destination allocations may enter direct reclaim/compaction. Neither changes ARMS's migration allocator flags. See `khugepaged_wait_work` and `alloc_hugepage_khugepaged_gfpmask` in [v6.18 khugepaged.c](https://github.com/torvalds/linux/blob/v6.18/mm/khugepaged.c); local 6.2 equivalents are `mm/khugepaged.c:2467` and `:768`.

A small timing change at proactiveness 20 therefore weakens only the tested background-policy explanation. It cannot rule out synchronous compaction in migration workers. A THP-defrag or khugepaged-sleep change must likewise be interpreted through its actual allocation/scan pathway and any resulting changes in memory layout.
