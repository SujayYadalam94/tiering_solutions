The same kernel image can boot with hundreds of MiB less allocatable memory, but this focused audit found no historical evidence that crashkernel or a debug-memory option supplied the missing May capacity. The two mechanisms with the right magnitude are a crash reservation and an enlarged SWIOTLB buffer; both remain hypothetical for May. Neither is unusually large in the current boot.

Evidence was captured without changing boot options, drivers, or VM settings. [Current privileged readbacks](current_boot_memory.json) contain the command line, crash counters, SWIOTLB debugfs, CPU masks, filtered physical memory map, and the retained GRUB backup. [The narrow history/config audit](boot400_kernel_evidence.json) records hashes and matches for three shell histories and 91 May–June host-setup editor snapshots from the existing catalog. No searched reservation/debug option appears in these histories. An earlier, broader script search also found no relevant change; the March Git matches `6b2f5ddf7` and `7d4508f98` were shell variables named `numa`, not boot NUMA emulation.

Crash placement and the extra low reservation are documented for [Linux 6.18 kernel parameters](https://www.kernel.org/doc/html/v6.18/admin-guide/kernel-parameters.html). The same documentation distinguishes `memblock=debug` logging from actual physical reservations. The saved GRUB backup has generic `debug`, logging, and initramfs-break options; these are not evidence of page-owner/debug-pagealloc allocation. The exact installed [SWIOTLB header](/usr/src/linux-headers-6.18.1-061801/include/linux/swiotlb.h:32) and [KFENCE header](/usr/src/linux-headers-6.18.1-061801/include/linux/kfence.h:27) supply the size constants above. The [installed kernel config](/boot/config-6.18.1-061801-generic:12790) supplies feature enablement.

Dynamic SWIOTLB growth deserves one distinction: background growth adds persistent pools to the allocator; mapping-specific transient pools are released when unmapped. Growth requires a failed slot search under bounce-buffer demand. The total `nslabs` counter includes persistent additions, so the current 64 MiB total and zero high-water usage provide no support for a surviving hundreds-of-MiB growth pool. There is no retained evidence that May devices needed enough bouncing to create one. See the exact [Linux 6.18 implementation](https://raw.githubusercontent.com/torvalds/linux/v6.18/kernel/dma/swiotlb.c), particularly `add_mem_pool`, `swiotlb_dyn_alloc`, `swiotlb_find_slots`, and `swiotlb_del_transient`.

The accounting distinction matters: ordinary boot crash/SWIOTLB reservations reduce managed memory and therefore `MemTotal`; they are not 400 MiB counted as free but forbidden to migration. Current node0 `MemTotal` is 4,626.941 MiB. The previously audited node0 `present - managed` gap is only 147.367 MiB total, including boot allocations such as SWIOTLB. A *historical* extra reservation could still have changed this, because the archived `4035/4040/4041 MiB` filename labels were script constants, not saved `MemTotal` measurements. We lack May command lines and zone readbacks to check that proposition. The current dmesg ring begins around 7,018 seconds after boot, so its lack of early reservation messages is not negative evidence about boot initialization.

No additional setting from this audit is historically justified to apply. Recovering an old complete command line or early boot memory map would discriminate a 384/512 MiB boot reservation from a later allocation; absent that evidence, reproducing the archived speed by imposing one would be a reconstruction experiment, not a recovered May setup.
