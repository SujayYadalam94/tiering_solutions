# Retained runtime-log evidence

The expanded inventory covers 9,863 accessible files under `logs/` and `times/`: 7,419 timing files, 2,088 text logs, and 224 Parquet files, plus plots, scripts, archives and graph data. The Parquet files total approximately 308.5 GB, but only their metadata/column statistics were inspected; graph payloads were not scanned. One unrelated 80 GB workload temporary directory was inaccessible to the file inventory. [Inventory](file_inventory.json), [text-log matches](text_log_matches.json), [all Parquet schemas and statistics](parquet_metadata.json).

**Historical ARMS failure counters were not recovered for the matched May/June ordinary BC runs.** The Parquet schemas have page selection counters but no migration-failure, THP-split, per-zone free-memory, or per-call-duration fields. This prevents reconstructing the original ARMS failure rate from these files.

**An actual May migration-error log survives for a different policy and workload.** `logs/mg.D.x-original/4029MiB_run1_hybridtier.log`, mtime May 11, contains 133 `move page error: 12` records. Each of those follows `move page ret -1`; the log explicitly prints `got ENOMEM` and retries. At the first such record, its reported node0 free memory is around 69,984 KiB. It identifies itself as HybridTier huge-page mode with a 4 GiB fast tier. [Count and hash](may11_hybridtier_mg_errors.json), [original log](/users/zimooo2/tiering_solutions/logs/mg.D.x-original/4029MiB_run1_hybridtier.log:215).

The retained HybridTier source prints these messages immediately after `numa_move_pages` in `tiering_runtime/hybridtier_huge.cpp:1170–1204`. The three earlier records printing error 2 follow positive aggregate returns, so their printed errno can be stale; they must not be treated as three verified ENOENT syscall failures. ENOMEM identifies the error, not the exact kernel allocation site. This log shows historical migration difficulty existed in a nearby experiment, but **it is not an ARMS log, not BC, and supplies no matching fast-run comparison**. It cannot establish the requested policy-specific historical change.

**The apparent May-to-June promotion-counter drop is confounded.** May 2 BC Twitter `run1.parquet` has zero `arms_score` and nonzero `model_score`; the June 6 `100050MiB_run1_train_arms.parquet` has zero `model_score` and nonzero ARMS scores. The saved April 30 training runner enables the model and comments out ARMS, while the saved June 6 runner explicitly chooses ARMS `_near_train`, node0, and 250/250 ms intervals. This is strong evidence of different producing policies/modes, not a matched ordinary-ARMS change. [Raw score/counter statistics](training_policy_comparison.json), [saved launchers](../setup/training_launch/), [launcher analysis](../setup/README.md).

Across May 2 Twitter run files, the largest recorded per-page `num_promotions` varies from 40 to 204; June 6's maximum is 20. Those numbers cannot be interpreted as kernel failures or successful migration counts. The May Git code increments the counters when it selects pages, before enqueueing worker tasks; cold-start virtual rows also explicitly zero the fields. [Exact Git excerpts](may_git_selection_counter_excerpts.txt). Older raw `score` values include extreme outliers, so those fields need validation before using them as evidence of actual policy choices.

**An unreachable Parquet blob was also inspected.** Git object `03706cb28ef60ea53612aed877e7505d5c26853f` is 301,200,432 bytes, with 7,123,233 rows and an ordinary training-feature schema. Its loose-object mtime is July 17, which dates storage, not execution. No producing path/run was recovered. The blob was streamed with bounded memory to inspect its 90,624-byte footer and compute a SHA-256; it was not materialized as a large working file. Its model-score field is zero and its ARMS score is populated, but it has no failure/THP counters or execution timestamp. [Recovered metadata and hash](unreachable_parquet_metadata.json). It therefore does not fill the missing matched May/June evidence.

**The old graph sizes match both current graph copies.** Cached metadata for the deleted `benchmark_old/graphs` files gives Twitter 12,732,173,745 bytes and Kron 17,966,800,881 bytes. Both current SSD and HDD paths have those exact sizes. [Comparison](graph_size_comparison.json). This weakens a graph-size-change explanation but cannot prove identical bytes, graph ordering, or physical storage because historical hashes/device identities were not retained.

**Old system journals do not reach the transition.** The privileged system-journal inventory starts September 7. The oldest rotated kernel log has three August 9 perf messages; the oldest rotated system log spans August 9–16. Neither contains May/June entries. Existing boot attribution uses the separately retained wtmp ledger, which preserves kernel/boot chronology without the old detailed allocator messages.

Of the 2,088 current text logs, 87 have mtimes before August 28. Most are `max_dram_hugepages` placeholders with `samples=0` or later training-event summaries. Their zero values are not observations of zero memory use. The May HybridTier MG log is the one other retained early runtime text log in this tree. Current September VM snapshots demonstrate the migration/compaction mechanism but cannot be substituted for missing historical counters.
